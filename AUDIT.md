# Repository Audit — WikiAutoTestsCypress

**Date:** 2026-08-05
**Scope:** Full source tree as of commit `06d839c` (branch `master`).
**Method:** Manual review of every tracked file (5 spec files, 3 page objects, config, package manifest, support files, docs) plus `git log`/`git ls-files` inspection and npm registry version checks.

---

## 1. Strengths (keep these)

- **Page Object Model is real, not decorative.** Spec files contain zero raw CSS/XPath selectors — every DOM interaction is behind a method on `WikipediaMainPage`, `WikipediaAuthenticationPage`, or `WikipediaSandboxPage`. This is the single most important thing to preserve.
- **Test names read like requirements.** `it('Handles a very long search query', ...)`, `it('Switch to a language where the article does not exist', ...)` — a non-technical reader can understand intent without reading assertions.
- **Real edge-case thinking in `search.cy.js`.** Unicode input, 300-char strings, special characters, numeric queries, mixed input — this is the kind of test design a recruiter can point to as evidence of QA judgment, not just tool usage.
- **Reporting pipeline exists end-to-end.** `mochawesome` → `mochawesome-merge` → `marge` → published `docs/` report on GitHub Pages is a legitimate, recognizable pattern, even though the current wiring has bugs (see below).
- **Independent test data per run in `editing.cy.js`.** `Test ${Date.now()}` avoids collisions between repeated runs against the same live sandbox page — the author was already thinking about shared external state.
- **Deliberate defensive UI handling.** `switchLanguage()` and `SandboxPage.edit()` both probe the DOM (`$body.find(...)`) before acting on optional dialogs (cookie banner / "start editing" modal) instead of assuming they're absent — the intent is sound even though the implementation is fragile (see Critical/Medium).

## 4. Cosmetic problems

- Comments in `wikipediaMainPage.js` narrate _what_ each line does (`// Method to navigate to the Wikipedia main page` directly above `visit()`) rather than explaining non-obvious _why_ — adds noise without information.
- Mixed indentation style: `WikipediaAuthenticationPage.js`/`WikipediaSandboxPage.js` use 2–4 space inconsistent indents; spec files mix 2-space (`navigation.cy.js`) and 4-space (`authentication.cy.js`, `language.cy.js`) indentation.
- `navigation.cy.js` has a stray leading blank line before the import statement.
- README has no badges, no license section, and mixes an audience-appropriate "Overview" with a Google Drive video-link list that will rot (Drive links are not access-controlled the same way as a public repo — worth double-checking sharing settings before pointing recruiters at them).
- No `LICENSE` file despite `package.json` claiming `"license": "ISC"`.

## 5. Architectural risks

- **No data/logic separation.** Search terms, language codes, edit summaries, and expected strings are inlined directly in spec files. A `fixtures/` or `utils/testData.js` layer would let scenarios be extended without touching test logic, and is explicitly requested in the target structure.
- **Reporting has two competing configurations stacked on top of each other** (`cypress-mochawesome-reporter` registered in `support/e2e.js` _and_ `cypress-multi-reporters` configured in `cypress.config.js`, which itself points at plain `mochawesome`). Three overlapping reporting mechanisms for one report is more fragile than one clear pipeline, and is the root cause of C2.
- **No environment abstraction.** `baseUrl` is hardcoded to production `en.wikipedia.org` with no test/staging alternative or `--env` override pattern, so there is no way to point the suite at anything else without editing the config file directly.
- **Authentication flow has no session caching.** Every `authentication.cy.js` test logs in from scratch via the UI (appropriate there, since login _is_ the feature under test), but if login were ever needed as a _precondition_ for other specs (e.g., editing while authenticated), there is no `cy.session()`-based reusable login helper — worth introducing as a `support/` helper for future use even though current specs don't strictly need it today.
- **Single flat `pageObjects/` folder with no shared base class or common locators file** — acceptable at 3 page objects, but the target structure (`cypress/pages/`) plus a `utils/` layer is the natural point to introduce a small shared "wait for stable DOM" helper instead of duplicating the `cy.wait(500)` + `$body.find()` probe pattern independently in two places.

## 6. Prioritized improvement list

1. **(Critical)** Untrack `cypress.env.json` from git going forward, add it to `.gitignore`, replace with `.env.example` / documented environment variables. _(Password rotation waived by repo owner — disposable test account.)_
2. **(Critical)** Fix `cypress.config.js` — pick **one** reporter configuration (`cypress-mochawesome-reporter`, since it's already registered in `support/e2e.js`) and remove the conflicting `cypress-multi-reporters` setup, or vice versa.
3. **(Critical)** Rewrite `package.json` scripts to be cross-platform (Node-based `rimraf`/`fs` instead of `rmdir`/`cp`), fill in `description`/`author`/`keywords`, remove the dangling `main: index.js`.
4. **(High)** Add `.github/workflows/cypress.yml` (Node LTS, `npm ci`, lint, test, upload artifacts, caching).
5. **(High)** Add ESLint + Prettier with cross-platform npm scripts (`lint`, `format`, `format:check`).
6. **(High)** Commit `package-lock.json` so `npm ci` is reproducible in CI.
7. **(Medium)** Restructure `cypress/pageObjects/` → `cypress/pages/`, normalize file casing, add `cypress/utils/` for shared helpers (e.g. dismiss-optional-dialog helper replacing the duplicated `cy.wait` + `$body.find()` pattern) and `cypress/fixtures/` test-data files for search terms/languages/edit text.
8. **(Medium)** Replace brittle literal-text assertions where a more stable alternative exists (e.g. assert on element existence/URL/class rather than exact MediaWiki copy) and document, rather than hide, the cases where external-text dependency is unavoidable.
9. **(Medium)** Upgrade Cypress to current LTS-equivalent latest (`15.x`) and re-verify all specs still pass.
10. **(Low)** Rewrite `README.md` in English for a Senior SDET/recruiter audience; add `ARCHITECTURE.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `LICENSE`, `.env.example`, `GITHUB_SETUP.md`.
11. **(Low)** Cosmetic cleanup: comment pruning, consistent indentation (delegated to Prettier once added), stray blank lines.

## What this audit deliberately does _not_ recommend

- **No migration to TypeScript by default.** The suite is small (5 specs, 3 page objects) and the audience is a recruiter skimming code, not a large team needing compile-time contracts across dozens of files. A full TS migration adds a build step and tooling surface that isn't earned by the current size. `ARCHITECTURE.md` will record this decision explicitly and re-open it only if the suite grows meaningfully — JSDoc types on page object methods are the proportionate choice instead.
- **No retry-on-failure blanket policy.** `cy.get(...).should(...)` already retries automatically under the hood; adding `Cypress.Config('retries', N)` suite-wide would mask the real flakiness sources (M5–M7) rather than fix them. Retries, if added, will be scoped to CI-only runs and documented as a mitigation for _external-site_ flakiness specifically, not a substitute for stable selectors.
- **No attempt to bypass Wikipedia's login/anti-automation protections.** Only the already-existing standard login form flow is kept.
